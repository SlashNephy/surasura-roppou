# ピン留めセマンティクスと自動保存（PR 2 設計）

Issue: [#197](https://github.com/SlashNephy/surasura-roppou/issues/197)

親設計: [2026-08-16-auto-offline-save-design.md](2026-08-16-auto-offline-save-design.md)

## 背景と目的

親設計の PR 2 にあたる。PR 1 で `savedLaws` を版ごとのレコードにし、現行版スロットを導入した。
本 PR では、法令を開いたときの自動保存を入れ、既存の「オフライン保存」トグルをピン留めに置き換える。

保存の意味が「ユーザーが明示的に残したもの」から「端末にキャッシュされているもの」へ移る。
そのうえで、ユーザーの「これは残したい」という意図をピン留めとして別に表現する。

## 決定事項

| 論点                   | 決定                                                             |
| ---------------------- | ---------------------------------------------------------------- |
| ピン留めの粒度         | 法令単位。ピン留めするとその法令の全版がエビクション対象外になる |
| ピン留めの保存先       | 新ストア `pinnedLaws`（keyPath `lawId`）                         |
| 自動保存の対象         | 開いた版すべて。現行版は `isCurrent: true`、過去版は `false`     |
| 過去版保存時の検索索引 | 更新しない。索引は現行版の本文だけを持つ                         |
| ビューアのバッジ       | ピン留め中のみ表示。「オフライン保存済み」表示は廃止             |
| 保存リストの構成       | 「ピン留めした法令」と「最近開いた法令」の 2 セクション          |
| 自動保存の失敗         | バナーを出さない。閲覧を妨げない                                 |
| 手動削除の導線         | PR 2 では設けない。PR 3 の LRU に委ねる                          |

## データモデル（DB v4 → v5）

ピン留めは法令単位、保存レコードは版単位なので、置き場所に選択肢がある。

### 案 A: `laws` レコードに `isPinned` を足す

移行は最小で済む。しかし `laws` は `Law` ドメイン型をそのまま格納するストアであり、
UI 都合のフラグを混ぜるとドメイン型に保存領域の関心が漏れる。

### 案 B（採用）: 新ストア `pinnedLaws`

```text
pinnedLaws
  keyPath: "lawId"
  value:   { lawId, pinnedAt }
  indexes:
    by-pinned-at : "pinnedAt"   ピン留め一覧の並び
```

ピン留めの有無がレコードの存在判定そのものになる。`savedLaws` の版単位モデルと直交するため、
PR 3 のエビクションは「`pinnedLaws` にある `lawId` は対象外」という 1 条件で書ける。

### 案 C: `savedLaws` の全版に `isPinned` を複製する

索引は引きやすいが、法令単位の事実を版ごとに複製するため、版が増えるたびに不整合の余地が増える。

### 移行（v5）

`savedLaws` にある `lawId` を重複排除して `pinnedLaws` に入れる。`pinnedAt` はその法令の最も古い `savedAt` を使う。
v4 までの保存はすべてユーザーの明示操作の結果なので、ピン留めの意図として引き継ぐ。

`pinnedLaws` は新規ストアなので、`createObjectStore` するだけで既存データは壊れない。
v4 移行と違い object store の作り直しは不要である。

## 自動保存

### トリガー

ビューアがオンライン取得に成功した直後に走らせる。次の 2 つの場合は保存しない。

- **オフラインフォールバック表示**（`loadedFromStorage: true`）: 保存済みの本文をそのまま表示しただけで、書き戻す内容がない
- **オフラインデモ法令**: そもそも e-Gov から取得していない

`loadLawViewerDocument` の中では行わない。ローダーは「表示する状態を作る」関数であり、
書き込みの副作用を持たせると、ローダーのテストとオフライン判定の両方が保存領域の状態に巻き込まれる。
呼び出し側（ビューア）が、表示する状態が確定したあとに保存を要求する。

### 保存する版

現行版として開いたときは `isCurrent: true`、基準日指定・版固定で開いたときは `isCurrent: false` で保存する。
`saveLawDocument` は同じ `[lawId, revisionId]` への再保存で `savedAt` を据え置き `updatedAt` だけを進めるため、
同じ法令を何度開いても版は増えず、`updatedAt` が LRU の入力として正しく更新される。

**例外: その法令に現行版が 1 件も無いときは、`isCurrent: false` で要求された保存でも現行版スロットに入れる。**
基準日を設定したまま使うユーザーは、開く法令すべてが `isCurrent: false` で保存要求される。
この例外が無いと、そのユーザーの `by-law-current` 索引は永久に空のままになり、
オフラインフォールバック（`getLawDocument` は現行版スロットしか見ない）がその法令について 1 件も読めなくなる。
「オフラインで読めることを既定にする」という自動保存の目的そのものが、その設定下で無効化されてしまう。
既存の現行版がある場合の振る舞いは変えない。過去版が既存の現行版を奪うことは引き続きない。

### 表示をブロックしない

本文を描画したあとに保存を走らせ、完了を待たない。保存中であることも表示しない。
自動保存はユーザーが要求した操作ではないため、その進捗は読書の関心事ではない。

## 検索索引

`SavedLawUseCase.save` は現在 `options` に関わらず `indexer.indexLaw` を呼ぶ。
このまま過去版を自動保存すると、現行版の検索索引が過去版の本文で上書きされる。

`indexLaw` を呼ぶかどうかは、要求した `options.isCurrent` ではなく、
`saveLawDocument` の**戻り値**の `isCurrent`（実際に現行版スロットへ入ったか）で判断する。

要求と結果は一致しないことがある。「保存する版」節の例外（その法令に現行版が 1 件も無いとき、
`isCurrent: false` で要求された保存でも空きスロットを埋めて現行版になる）がその典型で、
基準日を設定したまま使うユーザーは常に `isCurrent: false` を要求するため、要求値だけで
判断すると、空きスロットを埋めて実際には現行版になった版が永久に索引されない。
これは「表示される本文（`getLawDocument` が返す現行版）と索引の本文が食い違う」という
より広い不整合であり、要求ではなく結果で判断することでしか防げない。

したがって、空きスロットを埋めて昇格した版は索引される。既存の現行版があるために
`isCurrent: false` のまま保存された過去版は索引されない。

## UI

### ビューア

ボタン（デスクトップ / モバイルの 2 箇所）を「オフライン保存 / 保存解除」から「ピン留め / ピン留めを解除」に変える。
バッジはピン留め中のみ表示する。「オフライン保存済み」は自動保存の導入で常に真になり、情報量がなくなるため廃止する。

オフラインで読んでいることは既存の `loadedFromStorage` の表示が伝えるため、変更しない。

### 保存リスト

「保存済み法令」を 2 セクションに分ける。

- **ピン留めした法令**: `pinnedLaws` にある法令。`pinnedAt` 降順
- **最近開いた法令**: ピン留めされていない保存法令。`updatedAt` 降順

`updatedAt` 降順は PR 3 の LRU が消す順の逆順にあたる。次に消えるものが末尾に来る。

## エラー処理

**自動保存の失敗**: バナーを出さず、閲覧を続行させる。ユーザーが要求していない書き込みの失敗で読書を中断させる理由がない。
`QuotaExceededError` が続く状態は PR 3 の上限と `navigator.storage.persist()` で扱う。

**ピン留め操作の失敗**: 明示操作なので、既存の保存エラーと同じくバナーを出す。

**ピン留めされた法令の本文が無い場合**: 自動保存が失敗したまま（保存領域が満杯など）ピン留めすると、
`pinnedLaws` にレコードだけあり `savedLaws` に現行版が無い状態が生じうる。

これを避けるため、ピン留め操作は「表示中の本文を保存してからピンを立てる」1 つの操作にする。
保存に失敗したらピンも立てず、エラーバナーを出す。ピン留めは明示操作なので、失敗を黙って飲み込まない。

それでも不整合が残った場合（別経路で本文だけ消えた場合など）、読み取り側は該当法令を一覧から落とす。
ピン留めの記録自体は消さない。本文を引けないことと、ユーザーがピン留めした事実は別だからである。

ただし `deleteLawDocument`（法令をその全版ごと削除する明示操作）だけは例外で、同一トランザクションで
`pinnedLaws` のレコードも消す。全版削除はユーザーがその法令を捨てる意思表示であり、本文の無いピンだけを
残す理由がないからである。1 版だけを消す `deleteLawRevision` は法令自体が残りうるため対象外とする。

## テスト方針

### 自動保存（ビューア）

- 現行版で開くと自動保存され、`isCurrent: true` で入ること
- 基準日を指定して開くと `isCurrent: false` で保存され、現行版スロットが入れ替わらないこと
- オフラインフォールバック表示のときは保存を呼ばないこと
- 自動保存が失敗しても本文が表示され、エラーバナーが出ないこと

### 検索索引

- 保存結果が `isCurrent: true`（現行版スロットに入った）のときは `indexLaw` が呼ばれること
- 保存結果が `isCurrent: false`（現行版スロットに入らなかった）のときは `indexLaw` が呼ばれないこと
  （既存の現行版を奪わなかった過去版の保存を含む）

### ピン留め

- ピン留め / 解除で `pinnedLaws` が増減すること
- ピン留めを解除しても保存された本文は消えないこと
- 保存に失敗したときはピンが立たず、エラーバナーが出ること

### 移行

- v4 の保存法令が v5 でピン留めとして引き継がれること
- 同じ法令に複数版がある場合もピン留めは 1 件になること

型チェッカーが保証する事項は検証しない。

## PR 2 の非スコープ

- **件数上限と LRU エビクション**: PR 3。PR 2 単体では保存が増える一方になる
- **`navigator.storage.persist()`**: PR 3
- **版一覧の UI**: `listSavedRevisions` は引き続き UI から呼ばない
- **手動削除の導線**: PR 3 の LRU に委ねる。PR 2 で削除手段が一時的に無くなることは意図した状態である
